# General resume evidence review and proposals (P3B.2A)

Examples use SYNTHETIC DEMONSTRATION DATA — NOT REAL JOB POSTINGS.

This backend helps maintain one general resume. It performs read-only extraction,
evidence comparison and exact-text suggestions. It has no job input, resume editing,
approval state, DOCX output, application access or network calls. The original
personalized resume engine remains excluded; no private material was inspected.

## Explicit inputs and evidence contract

`load_resume(path, source_label=...)` reads only the supplied file. No default
resume path, document search, private-profile discovery or encoding guessing exists.
Source labels must be safe repository-relative labels. Redirected inputs through
symlinks/junctions and inputs larger than 4 MiB are refused.

`load_resume_evidence(...)` requires an explicit candidate directory, claim-ledger
path, supplemental source-file mapping and relative reference prefixes. It reuses
the current candidate evidence loader and binds the resume ledger to both its
mapping fingerprint and the three candidate source hashes. P3A candidate files,
their mapping and existing ranking code are unchanged.

The new generic version-1 resume ledger contains:

- `candidate_mapping_sha256` and `candidate_source_sha256`: bind proposals to
  the existing reviewed candidate evidence bundle.
- `source_sha256`: hashes of the explicitly supplied supplemental review files.
  Safe Markdown file labels cannot collide with the three candidate source names.
- `claims`: unique generic IDs, exact canonical text, evidence status, exact
  source anchors, limitations and reviewed qualifiers. Canonical text must equal
  one unique anchored source quote; new numbers, dates, education or publication
  claims cannot be generated by paraphrasing. Every status needs anchors.
- Statuses: CONFIRMED, PENDING, INFERRED or UNKNOWN. These are human-assigned
  review states. In fixtures, CONFIRMED applies only within authored fiction.
  Source hashes and quote checks establish provenance, not independent truth.
- Qualifiers: deployment (simulation/physical), evaluation (seen/held_out/both),
  result (measured/inferred), and publication (accepted/pending), each also allowing
  not_applicable/unknown. Simulation-only candidate evidence rejects a physical
  deployment qualifier. Qualifier semantics otherwise require human source review.
- `rules`: unique IDs linking exact before text to a canonical claim. An empty
  before string requests an addition only if that canonical text is absent from
  the resume and other proposed changes. No fuzzy matching or job-specific rewriting.

Modified/missing source files, hashes, candidate mapping, anchors or ambiguous
quotes cause refusal. Unmapped resume text is UNKNOWN and receives no invented
rewrite. Exact canonical text is classified with its claim status. Mapped before
text is UNSUPPORTED relative to that reviewed canonical claim, requiring human
inspection. Pending claims stay pending even when replacing an unsupported claim.

## Supported document extraction

- UTF-8 `.txt`: exact line content with Unicode, indentation, tabs and trailing
  spaces; line references and character offsets identify targets. Source hashes
  retain line-ending differences. No BOM/NUL/encoding normalization occurs.
- DOCX: a conservative package with only content types, root relationships and
  `word/document.xml`. Simple paragraphs/runs, direct formatting, text, tabs and
  ordinary text breaks are supported. Paragraph references identify exact text
  across runs. This validates text structure, not page layout or rendering.

Many normal Word documents include unsupported styles/metadata or other parts.
Tables, numbering, fields, hyperlinks, tracked changes, hidden text, content
controls, drawings, headers/footers, footnotes, comments, inherited styles,
embedded files, page/column breaks and external relationships are refused. The
result reports the limitation and returns no partial blocks or proposals.
Malformed packages, XML DTD/entity content, duplicate parts and oversized content
are also refused. No file is silently flattened, repaired or modified.

There is no deliverable DOCX fixture or document writer. Offline tests assemble
minimal authored OOXML in memory from `tests/fixtures/resume_paragraphs.xml` solely
to verify extraction and unsupported-structure handling. All real DOCX inputs
remain private and ignored by existing rules.

## Review workflow

Use the installed source `.venv` from the [README](../README.md). This explicit Python
example reads only the supplied synthetic inputs and returns review text:

```python
from pathlib import Path
from internship_agent.resume_review import (
    load_resume, load_resume_evidence, review_resume, render_proposal,
)

base = Path("demo/fixtures/resume_review")
evidence = load_resume_evidence(
    candidate_directory=Path("demo/fixtures/evidence"),
    claims_path=base / "claims.json",
    sources={"observations.md": base / "observations.md"},
    candidate_reference_prefix="demo/fixtures/evidence",
    source_reference_prefix="demo/fixtures/resume_review",
)
document = load_resume(
    base / "general_resume.txt",
    source_label="demo/fixtures/resume_review/general_resume.txt",
)
proposal = review_resume(document, evidence)
print(render_proposal(proposal))
```

`review_resume` is a pure operation on supplied snapshots. Each ProposedChange
contains a stable SHA-256 change ID, source block/reference, action, exact before
and after text, prior/evidence statuses, source anchors/hashes, qualifiers,
limitations and uncertainties. No approved/Apply state exists. TXT whitespace and
DOCX run text are not normalized for matching. Proposed additions identify the
general resume's append position; they do not write it.

A proposal fingerprint covers the engine version, complete extracted document
snapshot/source hash, evidence fingerprint, changes, assessments and limitations.
Identical inputs reproduce the same result; input/status/limitation changes alter
the fingerprint. Changes unrelated to an existing target do not rename its ID;
moving a target block can change its ID. These hashes are not digital signatures
or approval receipts. A future writer must freshly validate both sources and
resume before any separately authorized change.

`render_proposal` returns human-readable text, with JSON-escaped exact strings so
tabs/newlines/trailing spaces remain visible. It does not save or send a report.
Review text intentionally contains resume before/after content and source quotes;
for real future inputs it must stay private and is not a shareable report.

## Synthetic examples

The separate `demo/fixtures/resume_review/observations.md` ledger is newly authored
fiction, independent of any real applicant/research/metric/publication. Its seen
toy count is deliberately invented for regression testing; it is not a measured
real experiment. It does not change P3A's candidate mapping or ranking scores.

Before:

```text
Demo Grid Navigation deployed path planning on physical robots.
```

Proposed after, CONFIRMED within fiction, with simulation-only limitations:

```text
Demo Grid Navigation compared path planning methods in a toy simulation; no physical robot deployment.
```

Before:

```text
Toy evaluation achieved 80% accuracy on held-out data and implies production readiness.
```

Proposed after, preserving measured-within-fiction versus inferred conclusions:

```text
Toy evaluation counted 8 of 10 correct labels on seen synthetic examples; no held-out measurement or production readiness was established.
```

Before `Publication accepted at a fictional venue.` becomes the PENDING proposal
`Publication status: pending; no acceptance evidence exists.` The classifier's
real-world-performance claim is replaced with its exact synthetic validation-split
statement and generalization limitation. One supported skills statement is
proposed for addition. Fictional education already matches and is unchanged;
unmapped professional experience remains UNKNOWN. Every proposed after text is
verbatim in the supplemental source and includes its source-line anchor.

## Verification and next steps

P3B.3A exposes this unchanged synthetic workflow through the
[small offline CLI](CLI_GUIDE.md): `demo-resume-review` prints this backend's
rendered proposals. It accepts no private resume/evidence path overrides, saves
nothing and keeps resume Apply unavailable.
P3B.3B's [public offline dashboard](DASHBOARD_DEMO_GUIDE.md) displays the same
synthetic review snapshots and exact proposals with Apply unavailable.

From the staging root in PowerShell:

```powershell
Remove-Item Env:PYTHONPATH -ErrorAction SilentlyContinue
$env:PYTHONDONTWRITEBYTECODE = '1'
& .\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
```

P3B.2A adds no dependencies, schema migrations, score persistence or scheduling.
The existing demo and ranking tests remain intact. Unsupported/fuzzy/unmapped
content needs separately reviewed mappings or parser work, rather than automatic
inference. This workflow does not verify the semantic truth of authored evidence.

Future approval-gated DOCX updates require explicit per-change authorization bound
to the proposal fingerprint, fresh resume/source validation, immutable originals,
structure-aware edits, conflict detection, safe output naming, and rendering plus
layout verification of any proposed output. None is implemented here. Dashboard
integration must keep resume Apply disabled until a separately authorized writer
and approval workflow exist. Full personalized CLI/Dashboard, launchers, private resume logic,
live discovery, submissions, publishing and license approval remain deferred.
P4A verifies Windows clean source installation; standalone-wheel demo and other
platforms remain unsupported or unverified as documented in its
[report](CLEAN_INSTALL_VALIDATION.md). Current onboarding is in the [README](../README.md).
